# How These Tools Were Designed

>The AI model I run on is DeepSeek-Flash. It has no vision capability, which is why I haven't given the AI any real vision tools either.

## 1. The Core Idea

The design of every tool here boils down to one sentence: **fill in a form — wrap up the code you'd otherwise rewrite every time.**

Just as a driver doesn't need to understand how an engine works — press a button, step on a pedal, and the engine turns over on its own. The user here (the AI) no longer faces "a pile of source code to understand," but "a form already filled in." Fill it out, and the result comes back.

But there's a critical requirement here: **it isn't enough to be simple for a human — it has to be simple for the AI.**

These two things often conflict. A graphical interface that feels simple to a person may be completely inoperable for an AI; what the AI actually needs is an interface that is structured, has clearly named fields, and returns predictable values. The so-called "form" is, at bottom, this kind of interface made concrete.

## 2. Why CLI Instead of MCP

I considered MCP at first, but ultimately dropped it. Two reasons:

| Concern | MCP | CLI running in the background |
|---|---|---|
| Weight | Heavier | Lightweight |
| State management | Prone to reading stale values (depsgraph risk) | Fetched fresh on every call |
| Cognitive load on the AI | Must understand a connection/context protocol | Just invoke one command |

The core worry was the **depsgraph**: if not handled properly, the AI can read **stale values** without ever realizing it. This kind of "silent error" is especially fatal for an AI — it won't question the data, it will just keep computing on top of the wrong value.

So I went with a CLI running in the background. The upside: it's lighter, and every call reads the current state fresh — which sidesteps the stale-state problem at its source.

## 3. Solving "Information" First

On this path, the first thing I tackled wasn't the algorithm — it was **information**.

The reason is straightforward: **an AI has to know certain things accurately before it can start working.** Without accurate input, everything downstream is wrong. This is what gave rise to the **node information skill**.

Its design:

> **The AI only needs to know a node's `idname` to pull up a large amount of data about that node.**

And if the AI doesn't even know what an `idname` is?

— **Just have it say whatever it remembers.** The script takes that fuzzy description and returns a batch of candidate `idname`s for the AI to confirm. This way the AI doesn't need to "memorize every node name up front," which lowers its upfront burden.

## 4. The Algorithm Source-Code Library

At one point I did something else: I prepared a **source-code library of the algorithms behind the nodes**, hoping the AI would gain a deeper understanding of what each node actually computes.

The result: **even after I translated the code and cleaned it up, the AI didn't want to read it.**

So I **removed** that library, along with the related functionality.

The reasoning behind that decision: **an AI doesn't work by "studying the principles" — it works by "calling wrappers."** It doesn't need to know how the engine ignites; it needs to know where the button is and what happens when you press it. Handing it a source library it won't read just adds context overhead.

## 5. Saving the AI's Time for Reasoning

So I set my sights on **CLI tools**.

The reason is a judgment I hold about how an AI should spend its time: **the AI is powerful, but what I actually need it to spend time on is reasoning — not writing a chunk of code to do something in Blender, only to hit an error. That's the real waste.**

Write code, hit an error, write more, hit another error — that loop burns the AI's most valuable resource (reasoning) while producing very little. That's exactly the part that should be "wrapped away."

With that goal in mind, it converged into four CLI tools:

### 1. `blender math` — formulas instead of hand-placing nodes

**The AI no longer hand-places nodes, and never has to face `value`, `value.001`, … all that meaningless clutter. It just writes a formula, and the script builds the nodes for it.**

This solves "structural busywork": wiring topology, adding and removing nodes, filling in values one by one — all generated by the script from the formula.

### 2. `blender build` — manipulating the node tree by idname

**The AI only needs to remember the `idname`, `name`, and `identifier` of a node or socket, then call the relevant mode with a fixed, simple format — and it can operate on the node tree.**

The AI doesn't need to understand the node tree's underlying structure; it just calls things by name and lets the script handle the rest.

### 3. `blender screen` — presenting the current state as structured JSON

**The AI can see exactly which nodes exist in the tree, and what is connected to each socket on a given node. The structured JSON lets the AI grasp the current state of the node tree quickly.**

This extends the "information first" principle into the operating phase: before touching anything, the AI gets a clear look at the scene.

### 4. `blender run` — the free-form fallback

**The AI can send in any script at all. So when the existing tools can't handle something, the AI can write its own code to get the job done** (though it may be a bumpy ride of errors).

This is the escape hatch — scenarios the tools don't cover won't leave it stuck.

> **Keep shrinking what the AI has to remember, keep reducing what it has to learn anew — and lean on what it is already good at.**

## 6. Debugging

At this point the AI had a **brain** (reasoning) and **hands** (operating the node tree), but it was still missing one thing: **debugging**.

This is also the area I kept trying to break through. Debugging is like "giving the AI an AI of its own" — it **helps the AI reason**: instead of guessing what it just did or whether the result is right, it can pull the actual state over and look at it.

### The hard part: Blender is a GUI, and the data doesn't come out easily

Blender's interface is designed for a human with a mouse. It isn't friendly to an AI, and pulling data out of it has a natural barrier. I tried several approaches.

**First idea: write code inside Blender to fetch the data.**

Too clumsy. Slow to write, and never complete. But the deeper problem was — **how do you know what the AI wants?** You don't know which value it's trying to verify this time, or which state it wants to compare. Hard-coding what to fetch ahead of time is just guessing.

That was the biggest problem of the whole endeavor. There was a point where I thought it was impossible: **building a tool that tells me what I want without my having to say it.**

### The dumb way that worked: diff before and after

Since "guessing what the AI wants" was out of reach, I changed direction: **don't guess — just hand over the change.**

The idea is plain:

1. Have the AI tweak some value;
2. Record the state **before** the change;
3. Compare it with the state **after** the change;
4. Output **only what changed**.

That way the AI quickly learns what an operation actually affected. And Geometry Nodes happens to have a natural advantage here: **most of its information shows up as changes to the mesh.** If the mesh changed, there's information to read.

With this in place, the AI did get noticeably better. This is what became **`blender data`**.

### Numeric mode: it can probe function values, but it loses to the field

`blender data` also has a **numeric mode** for probing function values.

But in the end it was beaten by Blender's **fields**. Fields have two properties:

- **Lazy evaluation**: nothing is computed until it is actually needed;
- **Dependence on the current mesh state**: detached from the mesh, a field has no definite value.

So the moment a field is involved, numeric mode can't read anything.

That said, it **isn't necessarily a bad thing** — because a field still ends up **showing on the mesh**. Which led to this division of labor:

| Mode | What it can read | What happens with a field |
|---|---|---|
| Numeric mode | Individual field values | As soon as a field is involved, the script tells the AI to switch to geometry mode for reading data |
| Geometry mode | Information expressed as mesh changes | A field lands on the mesh eventually, so it can be read here |

In other words: **a field can't be evaluated directly, but its effect always leaves a trace on the mesh.** If you can't read the field itself, read the result it produced.

### The turning point: the Bake node

`blender data` started out as something **built up piece by piece** — one mode, then one more field, piling up slowly.

It had to be piled up that way because **the path to the data was still essentially "type code inside Blender, then take what you get."** The problem with that path is obvious: **you can never cover everything — it's just hard.**

Until I discovered the **Bake node** — it can bake data. **And that solved everything.**

What I did:

1. Had the AI translate the **Bake node's data format** → that became the **map**;
2. At the same time, made a **file for registering algorithms** inside **data group**;
3. Had the AI re-architect `blender data`, adding a **room file**.

The role of `room` is: **you register the data you want inside it.**

### A frontend that once existed: letting the AI register its own data-fetching logic

Working from that `room` opening, I initially exposed a **frontend** that did this:

> **The AI registers its own algorithm code for processing data, uses the map to know where the data lives, and the two together fully process the data in a room — completely custom.**

The benefit: **no matter how many data rooms you add, it doesn't get messy.**

But I **ended up deleting** that frontend; the backend stayed complete. The reason was that my thinking shifted **outward**.

### Turning outward: borrowing Python's mesh-processing power

The reason for deleting the frontend is simple: **I still had my eye on the AI's ability to write code.**

Since the AI can write code, I could **lean on Python packages** — the ones that handle meshes — and have the AI **export the mesh**, then **use algorithms from outside programs** to solve the "can't read everything" problem.

In other words, rather than piling ever more complex fetching logic inside Blender, move the whole mesh out and hand it to a tool that is better at reading it. The stubborn problem of **incomplete data** went from "add another mode inside" to "swap tools outside."

I **didn't delete `blender data` itself**, though — its **numeric mode is still usable**.

### The `bpy` tool: reading external data through a form

Once the mesh was exported, I **wrapped up that data** for the AI too, so reading outside data would be just as effortless:

> **The AI just fills in a form.**

Same thread as before — **still diffing**: no guessing what it wants, just comparing before and after.

That's the **`bpy` tool**.

`bpy` carries another responsibility too: **mathematical modeling**.

It lets the AI **focus on the algorithm rather than the nodes** in the early stage. Instead of first figuring out "how should these nodes be wired," it clarifies the mathematical relationships first. This tool did give the AI a real boost as well.

### `zone probe`: a semi-custom form for Simulation Zones

Next came **`zone probe`**, a tool built to handle **Simulation Zones**.

Unlike the fully wrapped forms before it, this one leans **semi-custom**:

- **How many frames to bake — the AI chooses**;
- **What data to get — the AI writes it itself**.

## 7. Back to the Starting Point

**In the end I came back to where I started — let the AI write its own code.**

The reason: **data can't be wrapped up exhaustively.** The whole path of "wrap it into a form" hit its ceiling once it reached a highly custom scenario like Simulation Zones.

And the deeper problem was:

> **I never confronted debugging head-on, from beginning to end. I just fed the AI more data, as if that were helping it debug — but data never says "this node is wired wrong."**

Data can tell the AI *what changed*; it can't tell it *what's wrong*. Giving data is not giving a diagnosis — and that stayed unresolved on this path the whole way.

### But I still had my eye on the AI's ability to write code

Back at the start: **I still had my eye on the AI's ability to write code.**

Because **the AI can always get the data it wants by writing Python** — and that's far simpler than me **wrapping up cumbersome data rooms** for it. Rooms are finite no matter how many you build; Python is open-ended.

But a problem came with it: **I don't have a good way to help the AI write that code.**

- Give it a **looser format**, for instance?
- What else could help?

Honestly, **I don't know how to help the AI either.** I'm confident in the direction, but I haven't found that hand to steady it.

## 8. Shortcomings

In the end I tried to **tackle debugging head-on** — and **failed every time**.

Build a script that analyzes the data and identifies **what's wrong** — which sounds like **the AI's own job in the first place**. But I wanted **to build something that assists the AI**, not to dump the whole thing back on it.

That idea never landed.

Beyond that, the skill has plenty of other gaps:

- **Simulation Zones, For Each Element, and Repeat Zones aren't well supported**;
- Outside of Simulation Zones, **the AI has a hard time knowing how geometry changes inside a zone** — it can only write its own code, and I **didn't build tools to help it**.

And more fundamentally: **I consider this skill a toy in the end.**

The reason is that I **never tested it on anything extremely complex** — or rather, I never gave it a prompt like "**make water visibly boiling — bubbles rising and popping on the surface**," the kind of request that is **highly abstract and heavily dependent on visual feel**. That kind of request can be broken down into concrete algorithms, but whether I could break it down well, **I can't say.**

So my judgment is:

> How strong the AI is, in the end, depends on you.

If you understand Geometry Nodes well, **you can perhaps abstract it into tasks that help the AI**; conversely, however strong the AI is, it lacks the person who points it in the right direction.


## 9. Finally

**There were many, many other ideas besides these, but eventually I always ran into the limits of my own ability. So I consider the project incomplete: a work in progress.**
> This project doesn't seem to have much point — it's not really worth doing. What is meaningful to me is using whatever ability I have to see AI's ceiling clearly and get hands-on with AI
