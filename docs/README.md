# Flow

一个无限画布的原型。左侧是团队列表（七条彩虹条），中间是画布，团队可以被拖成画布上的立方体节点，节点之间可以拉线。

这份文档只讲一件事：**这套代码靠什么规则组织起来**。看懂这一条，其余文件都是它的展开。

***

## 一、三段：输入 → 状态 → 画面

```
   输入  ──────▶  状态  ──────▶  画面
 点击 拖动 推送    唯一真相      状态算出来的结果
      ╲                          ╱
       ╲─── 直接改画面 · 禁止 ───╱
```

**输入**：任何"要求改变"的请求。点击、拖动、键盘是输入；后端推一条"这个节点开始跑了"也是输入。它们不碰画面。

**状态**：当前什么是真的。团队有几个、节点在什么坐标、侧栏聚焦的是谁、工作区进没进。全部放在 `js/state.js` 的形状里，只有 `business/*` 能写。

**画面**：状态的呈现。`teams.js`、`scene.js`、`hero.js`、`modals.js` 都只做一件事——读状态，把 DOM 画成那个样子。

动画不是第四段。**动画是两个状态之间的过渡**，它不引入任何新事实。

***

## 二、为什么中间那层不能省

如果规则写成"输入 → 画面"（跳过状态），下面这四类变化就没有位置：

| 变化来源               | 有用户输入吗     |
| ------------------ | ---------- |
| 后端推送：某个节点开始跑、跑完、出错 | 没有         |
| 时间：动画播完、轮询拿到新数据    | 没有         |
| 容器尺寸：窗口缩放、拖动分割栏    | 不是点击，是布局在变 |
| 派生：连线端点由两个节点的位置算出来 | 没人点它       |

只要有一条绕过去直接改 DOM，规则就守不住了——**规则一旦有例外，就没有规则**。

还有两个更实际的理由：

- **同一件事有多个入口时**，把规则写在回调里就要写多份。例子：「离开工作区要收侧栏」。挂在按钮上，将来加了快捷键、面包屑就得挂三遍，漏一个就是"退出了但侧栏还开着"。写在 `business/workspace.js` 里，任何路径退出都自动带走。
- **一个状态要影响多处画面时**，直接改画面就得改三处，且下次加一处又要记得改。

***

## 三、两条不变量

1. **画面是状态的函数**：同一个状态，画出来必须一模一样。不允许"这次进来是这样，上次进来是那样"。
2. **状态只能被意图改变**：没有第二条路。所有改状态的请求走 `core/bus.js` 的 intent，由 `business/*` 的 handler 落到 state。

意图不等于用户输入。它是**任何要求改变事实的请求**——用户点一下是一次，后端推一条也是一次。将来接真后端，只需要在 `business/api.js` 里换实现，画面那一侧一个字都不用改。

***

## 四、怎么判断某段代码违不违规

一条可操作的判据，能对每一行给出是/否：

> **有没有第二个地方需要读这个事实？**

- **需要** → 它属于状态，进 `js/state.js`。
- **不需要，但有明确的结束**（拖完、悬停结束、动画播完）→ 可以留在视图层，但**只能有一个主人**。
- **不需要，也没有生命周期**（纯粹的样式，如 cursor、透明度）→ 随便写。

第二种是灰色地带，容易出事。判断"有明确结束"要严格：如果这个事实在你收起界面、再打开之后**还在**，那它就没有结束，它属于状态。

## 五、审计结果

### 灰区

| 位置                                | 事实        | 现在谁读                       | 一旦…                                  |
| --------------------------------- | --------- | -------------------------- | ------------------------------------ |
| `js/teams.js` `.ti-option.active` | 产物选了哪一条   | `syncConfirm()`（同文件）       | 结果视图要显示"选中了哪个产物"时，就得搬进状态             |
| `js/teams.js` `.ti-toggle` 的 `on` | 选项一 / 选项二 | 没人                         | 提交表单要用这个值时就晚了                        |
| `js/teams.js` `.ti-input` 的内容     | 用户敲进去的文字  | 没人                         | 同上。现在它只活在这张卡里，卡片一重建就没了               |
| `js/splitter.js` 侧栏宽度             | 宽度像素值     | 没人（`trash.js` 读的是矩形，不是这个数） | 要"记住上次宽度"时。文件里已注明"只有它一个组件关心"，这句现在是真的 |

### 合法（但值得知道主人是谁）

| 位置                                          | 事实            | 为什么能留在视图层                            |
| ------------------------------------------- | ------------- | ------------------------------------ |
| `js/trash.js` `body.dragging-node`          | 删除区是否已武装      | 生命周期严格等于一次拖拽，且只有它自己写、CSS 和 `hit()` 读 |

| `js/canvas/scene.js` `just-born`            | 节点刚落地 700ms 内 | 纯视觉标记，自己 `setTimeout` 清理             |
| `js/hero.js` `in-workspace` 类               | 在不在工作区        | 派生自 `workspace.entered`，不是独立事实       |

## 六、目录与职责

```
js/
  core/          引擎零件，不懂业务
    store.js       状态容器：commit / subscribe / notify
    bus.js         意图总线：send / handle，永不抛错
    intent.js      所有意图名的清单（唯一真名表）
    dom.js / theme.js
  business/      唯一能写 business 状态的地方
    team.js        团队：增删改、聚焦
    canvas.js      节点与连线
    workspace.js   进出工作区、模式
    api.js         假后端。将来换成真请求，接口不变
  canvas/        画布这一个组件的内部
    scene.js       状态 → DOM
    view.js        平移缩放
    interactions.js 鼠标手势
    geometry.js    连线几何（纯函数，可单测）
  teams.js       侧栏组件：读状态画卡片
  hero.js        大标题：点击进入 / 离开工作区
  modals.js      两个弹出面板
  dragdrop.js    从侧栏把卡片拖成画布节点
  trash.js       拖拽时的删除区（单例）
  splitter.js    侧栏宽度拖拽
  main.js        装配：把上面这些接起来
```

一条边界规则：**组件之间不互相 import**。要跨组件做事，走 intent。

## 七、踩过的坑

**同一个视觉事实有多个主人，收尾就会打架。**
展开卡片的高度一度同时被三样东西计算：`flex-grow` 在分配、`height` 过渡在插值、`transform` 又在挪位置。三条曲线各自收敛，最后一帧互相补差额，表现为"动画结束又突然抖一下"。

彻底的办法不是把三条调得更准，而是**让一个事实只有一个主人**：其余卡片直接从布局里摘掉（不占位就不会参与博弈），只剩展开的那一张在变尺寸；位置则用 `transform` 单独补，与高度互不干涉。

**动画不该引入新的"事实"。** 它只负责把旧值演到新值；一旦它自己开始决定尺寸，就变成了第二个真相来源。
